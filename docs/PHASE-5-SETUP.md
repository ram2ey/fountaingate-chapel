# Phase 5: finance and Hubtel on Coolify

Hubtel merchant-contract confirmation and live activation are deferred at the user's request. Resume those steps when the merchant portal details are available; keep both payment gates false in the meantime.

The ledger uses PostgreSQL, GHS online payments and Africa/Accra reporting dates. Manual cash/bank records also support USD; values in different currencies never combine. No demo mode, seed payments or fake checkout exists.

## Deploy the ledger

1. Take a database backup and verify restore procedures before applying migration `0011_financial_ledger.sql` with the separate maintenance resource and migration owner. Existing contributions are copied with their IDs, donor relationships and giving dates; runtime writes to the old contributions table are revoked. Do not edit an already-applied migration. Run migrations twice to verify the checksum-based second run is a no-op.
2. Deploy the runtime image from `main`. The image traces `assets/fonts/NotoSans.ttf` and its SIL Open Font License for server PDF generation. No payment secrets belong in build arguments or `NEXT_PUBLIC_*` variables.
3. Use the existing runtime `DATABASE_URL` (`fgc_runtime`) and `AUTH_DATABASE_URL` (`fgc_auth`). These roles must not own tables, be superusers or bypass RLS. No Supabase service is needed.
4. Keep `PAYMENTS_ENABLED=false` and `HUBTEL_CONTRACT_CONFIRMED=false` while preparing the merchant integration. Authorized administrators can record cash/bank giving, make documented reversals, review monthly/annual totals and download PDF/CSV statements. Members can download their own linked giving records. Branch scope comes from the live session, never a browser branch override.

## Hubtel activation gate

Configure these **runtime-only** Coolify variables: `APP_ORIGIN` with the public HTTPS origin, `HUBTEL_CLIENT_ID`, `HUBTEL_CLIENT_SECRET`, `HUBTEL_MERCHANT_ACCOUNT` and `HUBTEL_CALLBACK_TOKEN`. Generate a callback token with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"` on a trusted machine and save it securely. The app supplies a callback URL for each attempt; do not manually discard its reference query parameter.

The hosted initialization adapter currently expects `POST https://payproxyapi.hubtel.com/items/initiate`, Basic authentication and the fields `totalAmount`, `description`, `callbackUrl`, `returnUrl`, `cancellationUrl`, `merchantAccountNumber`, `clientReference`. It expects `responseCode: "0000"`, `data.clientReference` and `data.checkoutUrl`. **This hosted contract could not be verified against the login-protected merchant documentation during implementation.** Confirm the endpoint, authentication, field casing, accepted amount range, GHS, card/mobile-money activation and returned checkout hostname with Hubtel before setting either gate to true. Adjust `lib/server/hubtel.ts` if your account uses a different documented contract. Current allowed checkout hosts are `pay.hubtel.com`, `checkout.hubtel.com` and `unified-pay.hubtel.com`; redirects, URL credentials and authentication parameters are rejected.

The authenticated verification adapter follows Hubtel's [official Flutter endpoint implementation](https://github.com/hubtel/hubtel-mobile-flutter-merchant-checkout-sdk/blob/master/lib/src/network_manager/checkout_endpoints.dart) and [official status response model](https://github.com/hubtel/hubtel-mobile-flutter-merchant-checkout-sdk/blob/master/lib/src/platform/models/checkout_payment_status_response.dart): GET `https://checkout.hubtel.com/api/v1/merchant/{account}/unifiedcheckout/statuscheck?clientReference={reference}`, with Basic authentication, and response `data.transactionID`, `data.clientReference`, `data.currencyCode`, `data.amount`, `data.status`. Recognized statuses are `paid`, `unpaid`, `expired`, `failed`. Confirm this API is enabled for the same hosted checkout account; a newer or account-specific status API requires an adapter change. Confirm any required outbound IP allowlisting using the Hetzner server's actual outbound address.

No payload-signature scheme was verified in the public Hubtel sources. The app therefore uses a random callback URL capability, constant-time token validation and an independent authenticated status lookup. A notification's body amount/status is never trusted. This capability is **not** a provider signature. If your merchant documentation specifies a signature, add its exact raw-body verification before enabling checkout. Suppress callback path/query logging in Coolify's proxy, application logs and external monitoring; the callback capability is a secret. Rotate it after exposure and reconcile attempts whose old callback URLs stop working. Do not accept forwarded host/origin headers to construct callback URLs.

Initialization is durable before contacting Hubtel. Retries of the same operation return the stored checkout URL; an uncertain initialization without a URL is not automatically repeated. Reconcile the visible reference with Hubtel before starting a new attempt. API failures never fabricate a paid record. Status queries have a 10-second timeout, 64 KiB response limit and no redirects. Callback bodies have a 16 KiB limit and 5-second read deadline. Verification is serialized per reference and successful lookups are throttled for 30 seconds across replicas.

### Required merchant staging checks

With Hubtel-approved test facilities and test credentials, validate successful mobile-money and card payments, cancellation, expiry, wrong amount/currency/reference, duplicate and out-of-order notifications, a network timeout during initialization, and status lookup after a lost notification. Verify the public HTTPS callback through Coolify, including its reference query and token; ensure unauthenticated calls fail. Inspect PostgreSQL to confirm one credit per successful attempt and no credit for unpaid, forged or mismatched results. Keep the gates disabled until these checks pass, then set both to true. No real charge or production deployment was performed by this implementation task.

## Ledger corrections and refunds

Cash/bank entries have unique branch references and operation IDs. Corrections append a reversal with a required reason; they never edit/delete the original. Partial reversals cannot exceed the remaining credit. Posting an incorrect entry is corrected by reversing it and recording a new entry, with a new operation/reference.

Hubtel's public status model does not document refund amounts. Do not infer refunds from a browser response or invent a `refunded` status mapping. Complete and independently confirm the refund in the Hubtel merchant portal first. Upload the portal confirmation as a private PDF in Documents. A finance administrator then selects **Record confirmed refund**, enters the actual refund reference, amount and reason, and selects their uploaded evidence. This action records an audited portal confirmation; it does not send money or claim automatic provider verification. The database requires a stored evidence version, the same branch, a finance capability, matching original currency/member/fund, a unique refund reference and a balance within the original credit. Partial refunds reduce net totals; a full refund marks the attempt refunded. Stale paid/failed notifications cannot remove recorded refunds.

Online `given_at` records the time the app first independently confirms payment, because the verified public status model does not provide a settlement timestamp. Manual date entry uses the selected Accra date at midnight; correction/refund dates use the time recorded. Reports are a giving ledger, not bank settlement or tax certification. Reconcile delayed year-boundary payments against Hubtel settlement records before closing the year.

## Reporting and exports

Reports filter the selected year or explicit date range and currency. Administrator donor filters use member IDs selected from the live directory; identical names never merge. Archived donors retain their history. Pending/failed attempts are separate from posted totals. Latest 50 attempts are shown per interval; staff can reconcile a specific reference through the authenticated verification endpoint. Ledger paging uses date/ID cursors. Exports fail explicitly above 10,000 matching entries; narrow the interval instead of accepting truncation.

PDF statements contain church, dates/timezone, donor, fund, currency, references, credits/adjustments and net totals. A receipt includes the original credit and all subsequent corrections, even outside the selected year. Noto Sans supports the supported glyph set; PDF export rejects missing glyphs explicitly and suggests CSV rather than corrupting donor text. CSV retains UTF-8, quotes/newlines and spreadsheet-formula protection; trusted decimal amount cells remain numeric, including negative adjustments. Downloads use protected server URLs without creating browser object URLs. Export activity is audited and responses use `no-store`. Exports do not replace database and private-file backups.
